# RMA-172 Diagnostic Bundle Export

## Scope

RMA-172 adds an explicit user-triggered export for bounded diagnostic evidence without
turning diagnostics into a second persistence channel for private application content.
The exporter consumes the RMA-170 structured log boundary and the RMA-171 typed
health/performance snapshot.

## Bundle format

A successful export is a ZIP archive containing exactly these redacted text entries:

- `manifest.json` — schema, user selection, redaction/exclusion policy, retained/dropped
  log counts, entry byte counts, and SHA-256 digests;
- `version-configuration.json` — provider, version, and device sections from the typed
  diagnostics snapshot;
- `performance-health.json` — simulation, rendering, and camera metrics including their
  available/degraded/unavailable state and reason;
- `logs.jsonl` — the recent structured diagnostic records, re-redacted at export time.

The runtime retains at most 512 structured records by default in a fixed-capacity ring
buffer. Overwritten records increment a dropped-record counter that is included in the
manifest. The exporter accepts no more than 4,096 records, caps each text entry at 2 MiB,
and rejects archives larger than 8 MiB.

## Privacy and user selection

The production UI exposes one action: **EXPORT REDACTED BUNDLE**. Its explicit selection
is `ReachyDiagnosticBundleUserSelection.RedactedOnly`.

The request model names possible sensitive selections so they cannot be added later as an
implicit boolean or hidden fallback, but RMA-172 deliberately rejects every non-redacted
selection. Credentials, raw audio, raw images, raw media, transcripts, and conversation
text therefore remain excluded. A future task may add a sensitive-content export only
with a separate privacy review and explicit user-consent UI.

This preserves the RMA-163 diagnostic admission rule and RMA-170 default-deny data-class
policy. Structured log fields are redacted before they reach the retained ring buffer and
are passed through `ReachyDiagnosticRedactor` again when the archive is built.

## Storage and failure behavior

The application writes user-requested archives under
`Application.persistentDataPath/diagnostics`. Filenames are generated by the application;
no imported/user-controlled path is used.

The core exporter:

- requires a `.zip` destination;
- refuses to overwrite an existing file;
- writes with `FileMode.CreateNew` to a temporary sibling path;
- validates all fixed archive entry names as simple contained filenames;
- moves the completed archive into place only after ZIP creation and size validation;
- deletes an incomplete temporary file on failure.

Export failures become an RMA-170 structured event containing operation and exception type,
not raw exception text. The diagnostics panel reports success/failure and the local path to
the user.

## Non-goals

RMA-172 does not scrape historical Unity/Android logs outside the RMA-170 structured ring,
does not export raw settings JSON, does not export media, and does not add transcript or
conversation persistence.
